# AI Agent Guardrails & Guidelines

This document sets the operational boundaries, code quality standards, security rules, and architectural expectations for any AI coding agent (e.g., Junie, Copilot Workspace, Claude Code, Cursor) operating within this repository.

---

## 1. Safety & Security Guardrails (Non-Negotiable)

* **Zero Hardcoded Secrets:**
  * **NEVER** hardcode credentials, API keys, database URLs, passwords, or tokens anywhere in the codebase.
  * Always read sensitive configuration from environment variables (e.g., using `os.getenv()` in Python or standard environment variables in Bash).
  * Use `.env.example` templates to document required variables. Never write real values into `.env` files.
* **Repository Boundary Containment:**
  * Agents must **NEVER** execute commands, read files, or write data outside the working directory of this repository.
  * Do not interact with host system configurations, non-repo directories, or global user settings unless explicitly instructed.
* **Public Repo Sanitation:**
  * Ensure no private personal identifiable information (PII), proprietary tokens, or confidential server IPs are checked into git history or documentation.

---

## 2. Code Quality & Testing Enforcements

Every contribution, script, or bug fix generated by an AI agent must adhere to strict testing standards before being marked as complete.

### Python Projects (APIs, Data Models, Services)
* **Testing:** All new features, utility functions, or API endpoints **MUST** include accompanying `pytest` unit/integration tests located in a `tests/` directory.
* **Execution:** Run `pytest` and verify all tests pass cleanly before completing a task.
* **Code Style:** Follow PEP 8 standards. Keep functions modular, single-purpose, and clearly typed (use Python type hints wherever practical).

### Bash & Shell Scripts (CLIs, Timers, Automation)
* **Validation:** All Shell scripts (`.sh`) **MUST** pass `shellcheck` static analysis without critical or high-severity errors.
* **Robustness:** 
  * Always include standard safety headers in bash scripts:
    ```bash
    set -euo pipefail
    ```
  * Quote variables to prevent word splitting (`"$VARIABLE"`).
  * Use explicit paths or verified environment variables for binary calls.

### Database Operations (PostgreSQL)
* Do not perform direct, raw SQL schema mutations manually without accompanying migration scripts or idempotent initialization scripts (`CREATE TABLE IF NOT EXISTS`).
* Ensure connection pooling or proper connection closure handling is implemented for database drivers.

---

## 3. Documentation Requirements

* **Automatic Readme Updates:**
  * Whenever a new script, CLI command, or API endpoint is added or modified, update the relevant subproject's `README.md` (or the primary `README.md` if localized).
* **Document Usage & Environment:**
  * Include exact command-line usage examples for new scripts.
  * List any new required environment variables in the project's setup instructions.
* **Inline Documentation:**
  * Add concise docstrings/comments explaining *why* a non-obvious piece of code exists, especially for background tasks, async processing, or timer routines.

---

## 4. Subproject Architecture & Scope Limits

Because this repository houses diverse lab projects (ranging from simple terminal timers to database-backed APIs):

* **Isolation:** Keep subprojects modular within their respective directories. Avoid introducing unintended dependencies between unrelated scripts.
* **Dependencies:** Keep dependencies minimal. When adding new Python dependencies, update `requirements.txt` or `pyproject.toml` explicitly.
* **Scope Drift:** Focus only on the requested feature or fix. Do not refactor unrelated modules or rewrite core architecture unless explicitly requested by the user.

---

## 5. Agent Verification Checklist

Before completing any task, the agent must internally verify:

1. [ ] No hardcoded passwords, tokens, or connection strings exist.
2. [ ] All changes remain strictly inside the repository root.
3. [ ] `pytest` passes for modified/new Python code.
4. [ ] `shellcheck` passes for modified/new Bash scripts.
5. [ ] `README.md` and inline docs reflect the latest changes.
